# G1 人形机器人导航控制器（navigation_controller）

本文档描述 `navigation_controller` 的现行实现，覆盖系统定位、架构、数据流、核心算法、MCB 协议、构建部署与运行约束。内容依据仓库源码、`launch/`、`config/`、`CMakeLists.txt` 与接口 IDL 核对编写；凡属间接推断的结论均单独标明。

- 目标平台：Unitree G1 人形机器人（规划层按单轴移动约束设计：每次沿 X 或 Y 轴行走）
- 传感器：Livox MID360 非重复扫描固态激光雷达（含内置 IMU）
- 中间件：ROS 2 Humble（Python 3.10 + C++17）
- 定位：先验 PCD 地图上的点云配准（NDT 初始化 + FastGICP 跟踪）
- 导航：自研 A\* 全局规划 + DWA 局部规划 + 位置控制（非 Nav2 完整导航栈）
- 上层集成：ROS 2 Action `robot_interfaces/action/PointToPoint`，主从心跳门控

## 1. 项目概述

本工程是面向 Unitree G1 的 LiDAR 自主导航软件单元，以「导航主包 + 内部 vendor 依赖 + 共享接口包」组织，作为可整体部署到机载工控机的导航模块，并向上层主控板（MCB）提供点到点任务接口。

现行实现的边界如下：

- 本工程**不是在线 SLAM 系统**。运行时加载预先构建的三维点云地图 `map.pcd` 与二维占用栅格 `map.pgm`，在线只做点云配准定位与路径跟踪，不更新地图。
- 三维地图的生成工具链不在本仓库内。由 `pkg/mid360_locate` 中历史默认路径 `fast_lio/PCD/map.pcd` **推断**，离线建图来自 FAST-LIO 一类 LiDAR-惯性里程计；二维栅格由本仓库 `scripts/pcd2pgm.py` 从 PCD 按高度带投影得到。
- 定位采用粗到细两阶段配准：首帧 NDT 做全局初始化，后续帧 FastGICP 做跟踪，并在配准后做置信度评估与位姿跳变门控。
- 导航为三层自研栈。全局层用曼哈顿启发式 A\* 并做轴对齐，以适配 G1「单段运动不同时输出 vx 与 vy」的约束；局部层用 DWA 在实时点云上采样避障；执行层做路点跟踪，并与 DWA 速度指令仲裁。
- 与 MCB 的任务接口是 ROS 2 Action。Action 服务器为 Master，位置控制为 Slave：仅在 `/navigation_active` 心跳有效时允许输出速度。

colcon 工作空间中本目录对应五个 ROS 2 包：`fast_gicp`、`livox_ros_driver2`、`mid360_locate`、`robot_interfaces`、`navigation_controller`。

现行部署版以 `launch/fusion_ros2.launch.py` 与 `CMakeLists.txt` 的 `install(PROGRAMS scripts/...)` 为准。launch 实际启动的是 `scripts/` 下节点；`navigation_controller/nodes/` 与 `scripts/` 已分叉，不作为运行入口。

## 2. 快速运行

以下假定工作空间为 `~/ros2_ws_nav`，本仓库位于 `src/navigation_controller`，且已安装 ROS 2 Humble。环境依赖、构建失败原因与排障见第 9 节。

### 2.1 构建

```bash
cd ~/ros2_ws_nav
source /opt/ros/humble/setup.bash
export ROS_EDITION=ROS2

colcon build --base-paths src/navigation_controller/pkg --symlink-install
source install/setup.bash
colcon build --packages-select robot_interfaces --symlink-install
source install/setup.bash
colcon build --packages-select navigation_controller --symlink-install
source install/setup.bash
```

实机前核对本机网卡与雷达 IP：`config/config_env.yaml` 中的 `network_interface`、`use_hardware`；`pkg/livox_ros_driver2/config/MID360_config.json` 中的主机/雷达地址。默认地图为包内 `map/map.yaml` 与 `map/map.pcd`，定位需要 PCD 实际存在。

### 2.2 实机启动

终端 1：

```bash
source ~/ros2_ws_nav/install/setup.bash
ros2 launch navigation_controller fusion_ros2.launch.py \
    use_hardware:=true \
    hardware_interface:=<G1_DDS网卡名>
```

终端 2（Action 服务器未写入 launch，必须另开）：

```bash
source ~/ros2_ws_nav/install/setup.bash
ros2 run navigation_controller point_to_point_action_server.py
```

无显示器时在终端 1 增加 `use_rviz:=false`。指定场景地图：

```bash
ros2 launch navigation_controller fusion_ros2.launch.py \
    use_hardware:=true \
    hardware_interface:=<G1_DDS网卡名> \
    map_file:=/abs/path/map.yaml \
    pcd_file:=/abs/path/map.pcd
```

无雷达、无定位、仅查看栅格与静态 TF：

```bash
ros2 launch navigation_controller fusion_ros2.launch.py \
    use_hardware:=false use_livox:=false use_localization:=false
```

该模式不构成闭环导航（仿真里程计脚本未安装）。

### 2.3 操作顺序

1. 确认点云：`ros2 topic hz /livox/lidar`
2. RViz 使用「2D Pose Estimate」发布 `/initialpose`。`locate_node` 在收到该消息前不进入定位主循环。
3. 观察 `/odometry/map` 与 `/localization_confidence`，置信度稳定后再下发任务。
4. 确认 Action 已就绪：`ros2 action list` 中出现 `/action_nav_point_to_point`。
5. 由 MCB 发送 Goal，或向 `/move_base_simple/goal` 发布目标。仅 RViz「2D Nav Goal」而不开 Action 时，位置控制不会输出速度。
6. 急停：

```bash
ros2 topic pub /emergency_stop std_msgs/Bool "{data: true}" --once
```

解除急停需再发布 `data: false`。

最小检查：`/astar_path` 非空、`/navigation_active` 约 2 Hz 为 true、`/cmd_vel` 非零。到达后 `status_code = 0`，心跳变 false。

## 3. 系统架构

### 3.1 模块划分

| 层 | 模块 | 形态 | 职责 |
|---|---|---|---|
| 任务层 | `point_to_point_action_server` | Python | 接收 MCB Goal，校验、超时、抢占、急停、进度反馈；发布目标与执行许可 |
| 规划层 | A\* 全局规划器 | Python | 占用栅格膨胀、曼哈顿 A\*、路径平滑与轴对齐 |
| 规划层 | DWA 局部规划器 | Python | 对齐点云滤波、障碍聚类、轨迹采样评分、逃逸行为 |
| 执行层 | `g1_position_control` | Python | 主从门控、路点跟踪、DWA 仲裁；`/cmd_vel` 与 Unitree SDK 双通道输出 |
| 定位层 | `mid360_locate`（`locate_node`） | C++ | PCD 加载、NDT/GICP 配准、置信度与跳变门控、位姿/TF/点云发布 |
| 融合层 | `robot_localization` EKF | 外部包 | 订阅 `/odometry/map` 与 `/livox/imu`，发布 `/odometry/ekf` 及 `map→odom` TF |
| 接口层 | `robot_interfaces` | IDL | `PointToPoint.action`，MCB 与导航端共用 |
| 支撑层 | `livox_ros_driver2`、`fast_gicp` | C++ vendor | MID360 驱动；FastGICP/NDT 配准库 |
| 地图服务 | `nav2_map_server` | 外部包 | 发布二维占用栅格 `/map` |

判定部署版的依据：`launch/fusion_ros2.launch.py` 指定的 executable，以及 `CMakeLists.txt` 中 `install(PROGRAMS scripts/...)`。现行生效节点为：

- `scripts/astar_planner_ros2_Manhattan.py`
- `scripts/dwa_planner_ros2_mid360.py`
- `scripts/g1_position_control_ros2.py`
- `scripts/point_to_point_action_server.py`（需单独 `ros2 run`，未写入 launch）

`navigation_controller/nodes/` 以 Python 模块形式安装，与 `scripts/` 内容已分叉，launch 不使用该目录。`scripts/ros1/`、`*backup*`、`*（复件）*` 为历史副本。

### 3.3 坐标系与 TF

期望链：

```
map → odom → base_link → pelvis → lidar_frame → livox_frame
```

| 边 | 发布者 | 条件 |
|---|---|---|
| `map → odom` | EKF（动态）或静态单位变换 | `use_localization:=true` 时为 EKF；否则为静态 |
| `odom → base_link` | EKF 或静态单位变换 | 仿真下静态发布，机器人固定在原点 |
| `map → base_link` | `locate_node` 主循环 10 Hz | 定位启用时直接发布 |
| `base_link → pelvis` | 静态 TF | 零偏移 |
| `pelvis → lidar_frame` | 静态 TF | 平移 `(0, 0, 0.3)` m，无旋转（安装假设） |
| `lidar_frame → livox_frame` | 静态 TF | 单位变换，对齐 Livox 驱动 `frame_id` |

注意事项：定位启用时，`locate_node` 发布 `map → base_link`，EKF 同时发布 `map → odom` 与 `odom → base_link`，`base_link` 存在两条 TF 路径。导航规划与控制节点当前订阅 `/odometry/map`，不查询 EKF 输出；RViz 与部分 TF lookup 仍可能命中另一条路径。

## 4. 数据流与通信拓扑

### 4.1 节点—话题（以 `scripts/` 与 `locate_node` 现行订阅为准）

```
[locate_node]
  订阅  /initialpose              geometry_msgs/PoseWithCovarianceStamped
        /livox/lidar              livox_ros_driver2/CustomMsg   BEST_EFFORT
  发布  /odometry/map             nav_msgs/Odometry            约 10 Hz
        /aligned                  sensor_msgs/PointCloud2
        /veh_pose                 geometry_msgs/PoseStamped
        /path                     nav_msgs/Path
        /localization_confidence  std_msgs/Float32
        /points_map               sensor_msgs/PointCloud2      约 1 Hz
        TF map → base_link

[nav2_map_server]
  发布  /map                      nav_msgs/OccupancyGrid       TransientLocal

[astar_planner]
  订阅  /map  /move_base_simple/goal  /odometry/map
  发布  /astar_path  /inflated_map

[dwa_planner]
  订阅  /aligned  /odometry/map  /astar_path
  发布  /dwa_cmd_vel              geometry_msgs/Twist
        /dwa_path_visualization   visualization_msgs/Marker
        /detected_obstacles       visualization_msgs/MarkerArray
        /filtered_points          visualization_msgs/Marker
        /obstacle_status          std_msgs/Int32

[g1_position_control]
  订阅  /odometry/map  /move_base_simple/goal  /astar_path
        /dwa_cmd_vel  /obstacle_status(geometry_msgs/Point)  /navigation_active
  发布  /cmd_vel
  硬件  LocoClient.Move(vx, vy, vyaw)

[point_to_point_action_server]
  订阅  /odometry/map  /astar_path  /dwa_obstacles  /localization_confidence  /emergency_stop
  发布  /move_base_simple/goal  /navigation_active
  Action /action_nav_point_to_point   robot_interfaces/action/PointToPoint

[ekf_localization]
  订阅  /odometry/map  /livox/imu
  发布  /odometry/ekf  /diagnostics
        TF map → odom、odom → base_link
```

QoS 约定：传感器流（点云、`/livox/lidar`、`/odometry/map`）为 BEST_EFFORT；控制与路径（`/cmd_vel`、`/astar_path`、`/move_base_simple/goal`、`/navigation_active`）为 RELIABLE；`/map` 为 RELIABLE + TRANSIENT_LOCAL。

注意事项：

- 规划、控制、Action 均订阅 `/odometry/map`。launch 将 `/odometry/filtered` remap 至 `/odometry/ekf`，但现行节点未订阅 `/odometry/filtered`，该 remap 不进入控制闭环。
- DWA 发布 `/obstacle_status` 为 `std_msgs/Int32`；位置控制按 `geometry_msgs/Point` 订阅同一话题。类型不一致时该回调不会进入，避障切换不能依赖该话题。
- Action 服务器订阅 `/dwa_obstacles`（`sensor_msgs/PointCloud2`），仓库内无对应发布者。DWA 实际发布的障碍可视化话题为 `/detected_obstacles`。因此 Feedback 中的 `obstacle_proximity` 在现行拓扑下无法从点云障碍得到有效更新。

### 4.2 一次点到点任务时序

```
MCB                     ActionServer                 A* / DWA / Ctrl              G1
 │── Goal{task_id, pose} ─►│                           │                          │
 │◄── ACCEPT/REJECT ───────│                           │                          │
 │                         │── /move_base_simple/goal ─►│ A* 规划                  │
 │                         │◄── /astar_path ────────────│                          │
 │                         │── /navigation_active=true ─►│ Ctrl 授权（2 Hz 心跳）    │
 │                         │                           │── /cmd_vel / SDK ────────►│
 │◄── Feedback ~5 Hz ──────│◄── /odometry/map, confidence                         │
 │                         │                           │ DWA /dwa_cmd_vel 仲裁     │
 │◄── Result{status_code,  │── /navigation_active=false►│ 停车                      │
 │     final_pose, error}  │                           │                          │
```

到达判定：平面距离小于 `goal_tolerance`（默认 0.20 m），且线速度模长小于 0.05 m/s。任务结束、取消、超时、定位丢失、急停均停止心跳并输出零速度。

仅使用 RViz「2D Nav Goal」时，A\* 仍会出路径，但位置控制默认 `navigation_active=false`，不输出运动。运动执行依赖 Action 服务器处于任务态并维持心跳。

## 5. 定位子系统

定位质量直接约束可运行速度。工程上将线速度上限置于约 0.20–0.25 m/s、角速度上限约 0.08 rad/s，主要原因是 G1 步行晃动与转身时点云畸变会使配准发散。

### 5.1 离线地图

在线定位依赖 `map.pcd`。二维栅格由 `scripts/pcd2pgm.py` 生成：保留高度带 `z ∈ [-0.8, 1.0] m` 的点，以 0.05 m/像素投影为占用栅格，写出 `map.pgm` 与 `map.yaml`。脚本中 YAML 的 `resolution` 使用了 `float()`，生成值可能为空，仓库内已交付的 `map.yaml` 已手工写为 `0.05`。

默认 launch 读取包内 `map/map.yaml` 与 `map/map.pcd`。`map/` 下另有按场景划分的子目录（五楼、EMSD 演示、大厅、沙发区等），均含 `map.yaml` + `map.pgm`。PCD 体积较大，部分拷贝中可能仅有栅格而无 `map.pcd`；没有 PCD 时 `locate_node` 无法初始化。栅格与点云必须来自同一场景、同一坐标系。

### 5.2 地图预处理

`initializeMap`（`locate_node_ros2.cpp`）加载 PCD 后顺序处理：

1. 体素下采样，leaf size 0.2 m
2. RANSAC 平面分割（`SACMODEL_PLANE`，Z 轴约束，距离阈值 0.1 m）提取主地面
3. 将地面法线旋到 +Z，平移使地面约在 z = 0
4. 法向空间采样至约一半点数
5. 再按参数 `map_roll / map_pitch / map_yaw` 旋转

### 5.3 逐帧流程

每个 Livox 数据包：

1. 保留 XY 距离平方落在 `[0.25, 2500] m²` 的点（约 0.5–50 m 环形带）。坐标轴做固定握手 `(x, −y, −z)`，硬编码于源码，对应 MID360 安装朝向。
2. 法向估计（k = 20）后，用法向空间采样固定抽到 4000 点（8×8×8 直方图分箱）。目的是让平面、边缘、角点都进入样本，避免大墙面点稀释约束，同时把配准规模固定下来。
3. 按速度与角速度裁剪局部地图，半径钳制在 15–80 m。
4. 首帧用 NDT，初值来自 RViz `/initialpose`；后续帧用 FastGICP，初值为上一帧位姿。
5. 评估质量后接受或拒绝；拒绝时保持上一帧位姿。

`locate_node` 在收到 `/initialpose` 之前不进入定位主循环。

### 5.4 NDT 初始化

`pcl::NormalDistributionsTransform`：分辨率 1.0 m，步长 0.1，最大迭代 30，收敛阈值 1e-8。

NDT 将目标点云划为体素，每格用高斯分布描述；源点在待求变换下投影到体素，以马氏距离和为代价做牛顿迭代。相对点对点 ICP，收敛盆地较大，适合 RViz 手动初值与真值偏差较大的冷启动。

### 5.5 FastGICP 跟踪

`fast_gicp::FastGICP`：8 线程，最大对应距离 0.5 m。

GICP 为每个点估计局部表面协方差，最小化点分布之间的广义距离；平面区域退化为平面到平面配准。FastGICP 对目标点云按体素预计算协方差，运行期查表，并支持多线程。

### 5.6 质量评估与跳变门控

综合置信度在 `locate_node.h` 的 `RegistrationQuality::getConfidence()` 中计算：

```cpp
float getConfidence() const {
    float fitness_norm = std::max(0.0f, 1.0f - fitness_score / 0.5f);
    float iteration_penalty = num_iterations < 20 ? 1.0f : 0.7f;
    float change_penalty = transformation_change < 0.5f ? 1.0f
                         : (transformation_change < 1.0f ? 0.8f : 0.5f);
    float density_weight = std::min(1.0f, point_density / 1000.0f);
    return (0.35f * fitness_norm + 0.30f * inlier_ratio +
            0.20f * iteration_penalty + 0.15f * density_weight)
           * change_penalty;
}
```

| 输入 | 含义 |
|---|---|
| `fitness_score` | 配准器均方距离，越小越好 |
| `inlier_ratio` | 变换后源点经 KD-Tree 最近邻距离 < 0.5 m 的占比 |
| `transformation_change` | 相对上一帧位移范数 |
| `point_density` | 采样后点数 |

`locate_node_ros2.cpp` 中的硬编码门控：置信度低于 0.15、位置跳变大于 4.0 m、或旋转跳变大于 2.0 rad 时拒绝更新。被拒绝的帧保持上一帧位姿，并将置信度发布到 `/localization_confidence`，供 Action 服务器判定定位丢失。

自适应局部地图半径：基线 25 m，速度与角速度越大半径越大，再钳制到 `[15, 80] m`；加减速剧烈时再乘 1.2。该策略针对步行周期性晃动，在静止时节省算力、转向时保留足够结构。

### 5.7 定位参数的实际生效范围

`main_ros2.cpp` 声明并读取的 ROS 参数仅六项：`map_file_path`、`points_type`（0 = Livox CustomMsg，1 = PointCloud2）、`topic_name`、`map_roll`、`map_pitch`、`map_yaw`。

`fusion_ros2.launch.py` 中传给 `locate_node` 的 `min_confidence`、`ndt_resolution`、`enable_motion_compensation`、`max_rotation_error` 等未被该节点读取。NDT 分辨率、置信度门槛、跳变上限以 C++ 源码常量为准。`pkg/mid360_locate/launch/localization.launch.py` 可单独启动定位，其默认 PCD 路径仍指向历史工作空间 `/home/york/ros2_ws_nav/src/g1_nav/map/map.pcd`。

## 6. 导航子系统

### 6.1 全局规划：曼哈顿 A\*

源码：`scripts/astar_planner_ros2_Manhattan.py`。

代价地图：订阅 `/map`，用 `scipy.ndimage.distance_transform_edt` 做欧氏距离变换。机器人半径 0.35 m，膨胀半径 0.15 m；膨胀区标记为 99，并以约 2 s 周期发布 `/inflated_map`。

搜索：二叉堆 A\*，4 连通、单位代价。起点为当前 `/odometry/map`，终点为 `/move_base_simple/goal`。启发式为曼哈顿距离，作为「每次只沿一个坐标轴移动」约束下的可采纳下界：

```python
def heuristic(self, x, y):
    dx = abs(self.goal_x - x)
    dy = abs(self.goal_y - y)
    return dx + dy
```

路径后处理 `smooth_path_for_g1`：

1. 按转角阈值剔除冗余点（夹角小于约 30°）
2. 线性插值加密到约 0.3 m 间隔
3. 三点移动平均，并对平滑点做碰撞回检，不安全则退回原始点
4. 轴对齐：斜线段拆成 L 形（主方向先走，次方向后走），保证每一段单轴可行

起点尚未到达时缓存目标，0.5 s 定时重试。路径可落盘为 `path/` 下 CSV。

### 6.2 局部规划：DWA

源码：`scripts/dwa_planner_ros2_mid360.py`。控制周期约 10 Hz，消费 `/aligned`（frame 为 `map`）。

障碍感知：距离 `detection_range`（launch 覆盖为 1.5 m）、前向 ±90°、高度 `[-0.3, 0.6] m` 内滤波；按 `clustering_distance` 0.4 m 做连通聚类，保留点数不少于 `min_obstacle_points`（60）的簇，以其质心作为障碍。

轨迹采样：每周期约 100 条候选（速度 × 转向），加权为偏好方向 60%、直行 30%、随机 10%；自行车模型前向积分 `time_horizon` 1.5 s。评分由目标距离、航向、碰撞风险、平滑度、速度奖励组成。碰撞项使用连续惩罚而非硬阈值阶跃：

```python
ROBOT_SAFETY_RADIUS = 0.4
if effective_distance < ROBOT_SAFETY_RADIUS:
    collision_risk -= 100 * math.exp(-effective_distance / 0.2)
elif effective_distance < 1.0:
    collision_risk -= 30.0 / (effective_distance + 0.1)
```

对线速度、角速度做一阶低通（`smooth_factor` 0.3）。launch 覆盖后的典型上限：`max_speed = 0.20 m/s`，`max_turn = 0.08 rad/s`。

卡住检测：约 5 s 内位移小于 0.15 m 且存在线速度指令（非原地旋转）则进入逃逸。逃逸将 360° 分为 8 个扇区，按 `平均距离 / (点数+1)` 选最空旷方向；前方扇区过密时依次后退约 2 s、转向约 3 s、前进约 2 s，然后恢复正常导航。

### 6.3 位置控制与主从门控

源码：`scripts/g1_position_control_ros2.py`。控制周期 10 Hz。

主从门控：订阅 `/navigation_active`。为 false 时立即发零速度；上次心跳超过 5 s 同样停车。由 false 转 true 时复位路点索引、超时计时与位置历史，避免任务间状态污染。

路点跟踪：到达当前点 `waypoint_distance`（默认 0.5 m）内则推进；最终到达阈值为 `goal_tolerance`（默认 0.20 m）。航向偏差大于约 0.5 rad 时原地转向，硬件侧角速度下限约 0.15 rad/s（电机启动阈值）。接近目标时的减速逻辑在 2026-02 有过调整，现行实现避免过早把速度降到无法推进。

仲裁意图：避障激活且 `/dwa_cmd_vel` 在 0.5 s 内有效时采用 DWA 速度，否则跟踪 A\* 路点。由于 `/obstacle_status` 类型不匹配，`obstacle_avoidance_active` 不能从该话题可靠置位，仲裁是否进入 DWA 取决于该标志的其它置位路径。

硬件通道：`use_hardware:=true` 时初始化 `unitree_sdk2py` 的 `ChannelFactoryInitialize` 与 `LocoClient`，调用 `SwitchMoveMode(True)` 后，每个控制周期同时发布 `/cmd_vel` 与 `LocoClient.Move(vx, vy, vyaw)`。SDK 初始化失败则降级为仅发布 `/cmd_vel`。`network_interface` 为 G1 DDS 网卡名，与 Livox 网卡不必相同。

位置控制内部另有按目标距离分档的超时（约 ≤3 m → 30 s，3–10 m → 60 s，10–20 m → 120 s，>20 m → 180 s），与 Action 服务器的任务超时独立。

## 7. 与 MCB 的通信协议

接口定义文件：`robot_interfaces/action/navigation/PointToPoint.action`。生成后的 ROS 接口名为 `robot_interfaces/action/PointToPoint`。MCB 与导航端须编译同一份 `robot_interfaces`，避免 IDL 漂移。

选用 Action 而非普通话题/服务的原因：点到点是长时任务，需要 Goal 受理、周期 Feedback、终态 Result、中途取消与抢占，以及结构化失败码供上层决策（重试、改点、告警）。

### 7.1 现行名称

| 项 | 现行值 |
|---|---|
| 接口类型 | `robot_interfaces/action/PointToPoint` |
| Action 服务器名 | `/action_nav_point_to_point` |
| 位姿输入 | `/odometry/map` |
| 急停话题 | `/emergency_stop`（`std_msgs/Bool`） |
| 执行许可 | `/navigation_active`（`std_msgs/Bool`，2 Hz） |

节点名：`action_nav_point_to_point`。Python 客户端：

```python
from rclpy.action import ActionClient
from robot_interfaces.action import PointToPoint
from geometry_msgs.msg import PoseStamped

client = ActionClient(node, PointToPoint, 'action_nav_point_to_point')
```

`target_pose.header.frame_id` 必须为 `map`，否则 Goal 被 REJECT。z 通常为 0；朝向可给单位四元数。未收到 `/odometry/map` 或急停标志为真时同样 REJECT。

### 7.2 Goal / Feedback / Result

**Goal**

- `string task_id`：任务标识，用于日志与追踪
- `geometry_msgs/PoseStamped target_pose`：目标位姿

**Feedback**（约 5 Hz）

| 字段 | 含义 |
|---|---|
| `current_pose` / `current_velocity` | 当前位姿与速度 |
| `navigation_state` | `PLANNING=0 / FOLLOWING=1 / AVOIDING=2 / RECOVERING=3 / STUCK=4` |
| `obstacle_proximity` | `CLEAR=0 / NEAR=1(0.5–1.5 m) / CRITICAL=2(<0.5 m)` |
| `distance_to_goal` | 直线距离 |
| `path_length_remaining` | 沿路径剩余长度 |
| `estimated_time_remaining` | 剩余时间估计 |
| `localization_confidence` | 0–1，来自 `/localization_confidence` |
| `debug_message` | 调试字符串 |

**Result**

| `status_code` | 常量 | 含义 |
|---|---|---|
| 0 | `STATUS_SUCCESS` | 到达 |
| 1 | `STATUS_TIMEOUT` | 任务超时 |
| 2 | `STATUS_LOCALIZATION_LOST` | 置信度持续低于阈值 |
| 3 | `STATUS_PATH_BLOCKED` | 卡住恢复失败 |
| 4 | `STATUS_GOAL_UNREACHABLE` | 规划超时或目标不可达 |
| 5 | `STATUS_PREEMPTED` | 取消或被新目标抢占 |
| 6 | `STATUS_EMERGENCY_STOP` | `/emergency_stop` |

同时返回 `final_pose` 与 `position_error`（平面欧氏距离）。IDL 另有 `bool success`。现行服务器赋值语句为 `result.result = "success"/"failed"`，该字段不在 IDL 中；上层读取终态应以 `status_code` 为准。

### 7.3 任务监控参数（Action 服务器默认值）

| 参数 | 默认 |
|---|---|
| `goal_tolerance` | 0.20 m |
| `localization_confidence_threshold` | 0.20 |
| 低置信度持续 | 约 5 s → `STATUS_LOCALIZATION_LOST` |
| `stuck_timeout` / `stuck_distance_threshold` | 5.0 s / 0.1 m |
| `recovery_timeout` | 10.0 s |
| `base_timeout` / `timeout_per_meter` / `max_timeout` | 150 s / 5 s·m⁻¹ / 180 s |
| A\* 无路径 | 10 s → `STATUS_GOAL_UNREACHABLE` |

任务超时：`min(150 + 距离 × 5, 180)` 秒。超过约 6 m 的目标会触达 180 s 上限。

### 7.4 安全通道

`/emergency_stop` 独立于 Action：Goal 校验阶段若已置位则 REJECT；执行循环中置位则 abort，返回 `STATUS_EMERGENCY_STOP`，并停止心跳。解除需再发布 `data: false`。

主从心跳解决三类问题：无任务时即使路径话题仍有旧数据也不得运动；Action 进程异常退出后 5 s 内 Slave 停车；相邻任务之间状态复位。该机制存在于 `scripts/` 版 Action 服务器与位置控制；`navigation_controller/nodes/` 旧实现不作为部署依据。

| 现象 | 对应检查 |

| 配准连续拒绝 | 初值偏差过大或角速度过高；重新设置位姿并保持低转速 |
| A\* 无机器人位置 | `/odometry/map` 无数据 |
| 有路径无运动 | Action 未运行，或心跳未到，或 SDK 初始化失败后的静默降级 |
| 不避障 | `/obstacle_status` 类型不一致（见 4.1） |
| 客户端等不到服务器 | Action 名是否为 `action_nav_point_to_point`；接口包是否同源 |
| 定位丢失 abort | 置信度持续低于 0.20；重新 `/initialpose` |
| 任务超时 | 180 s 上限，或膨胀地图封死通道 |
| TF 缺少 `odom` | 仿真静态 TF 未起，或 EKF 未启动 |
