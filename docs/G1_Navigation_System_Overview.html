1. Executive Summary

This document presents the technical method and principles of the G1 Humanoid Robot Autonomous Navigation System. The system enables the Unitree G1 humanoid robot to autonomously navigate in indoor environments by integrating real-time 3D LiDAR perception, sensor fusion-based localization, global/local path planning, and direct hardware locomotion control.

Key Principle: The system follows a layered architecture separating Sensing → Localization → Planning → Control, where each layer operates as an independent ROS 2 node communicating through well-defined topics and actions. This modularity allows independent tuning, testing, and replacement of any layer.

2. System Architecture

The navigation stack is built on ROS 2 Humble and organized into five distinct layers. All nodes are launched through a single unified launch file (fusion_ros2.launch.py) with environment-driven configuration via config_env.yaml.

2.1 Layered Architecture

Sensor Layer Livox MID-360 Driver — publishes raw 3D point cloud (/livox/lidar) and IMU data (/livox/imu) at native rates
Perception Layer Localization Node (mid360_locate) — point cloud registration against a prior PCD map using Fast-GICP; outputs pose at 2–4 Hz
EKF Fusion Node (robot_localization) — fuses LiDAR pose + IMU angular velocity; outputs smooth pose at 50 Hz
Planning Layer A* Global Planner — computes collision-free global path on 2D occupancy grid with obstacle inflation
DWA Local Planner — dynamic obstacle avoidance using real-time 3D point cloud clustering
Control Layer Position Controller — waypoint tracking, speed regulation, DWA integration, timeout recovery
Hardware Layer Unitree SDK Interface — direct locomotion commands to G1 via DDS over Ethernet

4. Localization — LiDAR-Inertial Fusion

Localization is the most critical component of the navigation system. It answers the fundamental question: "Where is the robot on the map right now?" The system uses a two-stage architecture combining high-accuracy but low-frequency LiDAR scan matching with high-frequency IMU-based prediction.

4.1 Stage 1: LiDAR Scan Matching (mid360_locate)

The mid360_locate node performs real-time point cloud registration between the incoming LiDAR scan and a pre-built 3D point cloud map (.pcd file). This provides the absolute position and orientation of the robot in the map frame.

Algorithm: Fast Generalized ICP (Fast-GICP)

Generalized Iterative Closest Point (GICP) is a point cloud alignment algorithm that extends classic ICP by modeling both the source and target point sets as probability distributions rather than rigid point correspondences. This produces more robust and accurate alignment, especially with sparse or noisy data typical of LiDAR scans.

The Fast-GICP implementation used in this system adds multi-threaded parallel computation using OpenMP, achieving real-time performance (2–4 Hz registration rate) on embedded platforms. VGICP (Voxelized GICP) and NDT (Normal Distributions Transform) backends are also available as alternative registration strategies.

Point Cloud Deskew (Motion Compensation): During a LiDAR scan acquisition (~100 ms), the robot may move, causing the point cloud to be "smeared." The system integrates IMU gyroscope measurements over the scan duration to compute a per-point rotation correction, effectively undoing the motion distortion before registration. This is essential for maintaining accurate alignment when the robot is walking.

4.2 Stage 2: Extended Kalman Filter (EKF) Sensor Fusion

The LiDAR-based localization provides accurate absolute position at 2–4 Hz, but the G1 humanoid robot's walking motion requires continuous pose estimates for stable control. The Extended Kalman Filter (EKF) bridges this gap by fusing multiple sensor sources into a smooth, high-frequency pose estimate.

Fusion Strategy

Input Source 1: LiDAR Localization

  • Topic: /odometry/map
  • Rate: 2–4 Hz
  • Fused states: x, y, yaw (absolute position & heading)
  • Role: Provides the absolute reference — corrects drift

Input Source 2: IMU (MID-360 built-in)

  • Topic: /livox/imu
  • Rate: ~200 Hz
  • Fused states: angular velocities (vroll, vpitch, vyaw) + linear acceleration (ax, ay)
  • Role: Provides high-frequency prediction between LiDAR updates
Critical Design Decision — IMU Orientation NOT Fused: The IMU's absolute orientation (roll, pitch, yaw from the orientation field) is deliberately excluded from the EKF fusion. Without an external magnetometer or visual reference, the IMU's integrated heading drifts over time and would conflict with the LiDAR-derived heading. Instead, only the angular velocity (gyroscope raw output) is fused — this provides excellent short-term rotation prediction without cumulative drift. The absolute heading reference comes exclusively from the LiDAR scan matching.

5. Global Path Planning — A* Algorithm

The global planner computes a collision-free path from the robot's current position to the target destination on a 2D occupancy grid map. It uses the A* (A-star) search algorithm — one of the most well-established and efficient graph search algorithms for finding optimal paths.

5.1 A* Algorithm Principle

A* evaluates nodes by combining two cost functions:

  • g(n) — the exact cost from the start node to the current node n
  • h(n) — a heuristic estimate of the cost from n to the goal
  • f(n) = g(n) + h(n) — the total estimated cost through node n

The algorithm always expands the node with the lowest f(n) value, guaranteeing the shortest path when the heuristic is admissible (never overestimates the true cost).

5.2 G1-Specific Enhancements

Obstacle Inflation

Before planning, the raw occupancy grid is inflated to account for the physical dimensions of the G1 robot. The inflation radius is computed from:

  • Robot radius: 0.35 m (G1 body width + safety margin)
  • Inflation radius: 0.25 m (additional buffer around obstacles)

The inflation uses Euclidean Distance Transform (scipy.ndimage.distance_transform_edt) to compute the exact distance from every free cell to the nearest obstacle, then marks all cells within the inflation radius as impassable.

Humanoid-Aware Heuristic Function

Unlike wheeled robots that can turn in place easily, the G1 humanoid has non-holonomic constraints — turning requires time and additional walking distance. The heuristic function incorporates this by adding a Dubins-path-inspired turning cost:

  • Base heuristic: Euclidean distance to goal
  • Turning penalty: |heading_difference| × minimum_turn_radius (turn radius ≈ 0.6 m)
  • Large-angle penalty: additional cost for turns exceeding 135° (near U-turn scenarios)

Path Smoothing

The raw A* grid path contains many sharp right-angle turns. A post-processing step applies path smoothing optimized for the G1 gait, producing gradual curves that the humanoid robot can follow without stopping to turn.

6. Local Planning & Obstacle Avoidance — DWA

While the A* planner provides a global path on the static map, the real world contains dynamic obstacles (people, furniture, doors) that are not in the pre-built map. The Dynamic Window Approach (DWA) handles real-time obstacle avoidance by evaluating candidate velocity commands over a short time horizon.

6.1 DWA Algorithm Principle

DWA operates in the robot's velocity space (linear velocity v, angular velocity ω). At each control cycle (10 Hz), it:

  1. Generates candidate velocities within the dynamic window — the set of (v, ω) pairs reachable given the robot's acceleration limits
  2. Simulates forward each candidate for a time horizon (1.0 s), predicting the resulting trajectory
  3. Scores each trajectory using a multi-objective cost function
  4. Selects the highest-scoring velocity command and publishes it

DBSCAN-style Clustering

Filtered points are grouped into clusters using a density-based spatial clustering algorithm. Each cluster with ≥40 points is treated as a distinct obstacle, characterized by its centroid coordinates and point count. The clustering distance threshold is 0.3 m.

Each candidate trajectory is evaluated by a weighted combination of five objectives:

Continuous Collision Penalty: Unlike simple binary collision checks, the system uses a continuous penalty function that smoothly increases as the robot approaches an obstacle. This prevents score discontinuities that could cause oscillating behavior, and provides stronger avoidance force as the robot gets closer to danger.

6.4 Stuck Detection & Escape Behavior

The DWA planner includes an intelligent stuck detection and escape mechanism specifically designed for the G1 humanoid's limitations:

  1. Detection: If total displacement < 0.15 m over 5 seconds while linear commands are active
  2. Obstacle Analysis: 360° space divided into 8 sectors; obstacle density calculated per sector
  3. Escape Sequence:
    • Phase 0 (2s): Reverse if front sector is blocked
    • Phase 1 (3s): Rotate toward the clearest sector
    • Phase 2 (2s): Advance in the escape direction

Why Low Angular Speed? The G1 humanoid's localization relies on LiDAR scan matching. Rapid rotation causes severe point cloud smearing that even IMU deskew cannot fully compensate, leading to localization failures. The angular speed is therefore strictly limited to 0.08 rad/s to maintain reliable localization throughout navigation.

8. Map Management

The system uses two complementary map representations for different purposes:

3D Point Cloud Map (.pcd)

  • Used by: Localization (mid360_locate)
  • Format: PCD (Point Cloud Data)
  • Content: Full 3D structural representation
  • Purpose: Reference for scan-to-map registration
  • Creation: Built offline via SLAM or manual scanning

2D Occupancy Grid (.pgm + .yaml)

  • Used by: A* Global Planner
  • Format: PGM image + YAML metadata
  • Content: 2D bird's-eye view with free/occupied/unknown cells
  • Purpose: Fast 2D path planning
  • Creation: Converted from PCD using pcd2pgm.py tool
Map Consistency: Both maps are derived from the same environment scan, ensuring spatial consistency between the localization reference and the planning grid. The pcd2pgm.py utility automates the conversion process, projecting the 3D point cloud onto a 2D plane with configurable height thresholds and resolution.

10. Safety & Reliability

10.1 Localization Health Monitoring

  • Confidence Score: Published on /localization_confidence after each registration. Downstream nodes can gate navigation based on confidence thresholds.
  • Ready Signal: /localization_ready only becomes true after 3 consecutive confident registrations — prevents premature movement.
  • Jump Rejection: Position jumps >4 m or rotation jumps >2 rad between consecutive frames are automatically rejected as outliers.

10.2 Navigation Safeguards

  • Action Server Gating: When allow_rviz_goal_without_action: false, the robot only moves when an active Action is in progress — prevents accidental RViz-triggered motion.
  • Timeout Detection: The position controller detects when expected progress is not being made and can trigger replanning or safe stop.
  • DWA Command Timeout: If the DWA planner fails to publish for >0.5 s, the controller falls back to pure path following or stops.
  • Graceful Degradation: The system supports simulation mode for testing without hardware, and gracefully handles missing packages (e.g., Livox driver not built).

10.3 Conservative Velocity Policy

Safety-First Speed Limits: The G1 humanoid navigates at a conservative 0.25 m/s (vs. its maximum capability) with angular velocity capped at 0.08 rad/s. These limits are specifically tuned to maintain localization stability — faster speeds would cause LiDAR scan degradation and potential localization loss, which could result in the robot walking into obstacles.
