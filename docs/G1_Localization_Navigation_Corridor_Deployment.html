Localization & Navigation Architecture for Unitree G1 in Narrow Corridors

A client-facing overview of the sensing, mapping, planning, and control stack — designed for tender review, stakeholder alignment, and deployment in structured environments (1 m corridors, crab-style motion, machine-facing).

Deliverable: System architecture & data-flow specification Stack: navigation_controller + Nav2 ecosystem + custom planners

For operations

Repeatable, map-based positioning so the robot always knows where it is relative to machines and corridors.

For safety

Layered obstacle handling: global map constraints + real-time LiDAR costmap + behaviour overrides.

For integration

Standard ROS 2 interfaces (nav_msgs, geometry_msgs, tf2) — vendor-neutral and audit-friendly.

Plain-language summary: The robot builds a mental “floor plan” (map), uses a spinning laser to know its position on that plan, plans a route to the goal, checks for unexpected obstacles, then sends motion commands to the G1 locomotion layer. The diagrams below show which software blocks perform each step and which industry-standard libraries they rely on.

1 End-to-end system architecture (swimlane view)

Each horizontal band is a functional layer. Data generally flows left → right and top → bottom through sensing, state estimation, planning, and actuation. Package names follow ROS 2 conventions; techniques are called out in italics inside each block.

Figure 1 — Full stack (localization + navigation)

How to read this: Layer A produces pose and aligned point clouds; Layer B supplies the global grid and fused odometry; Layer C runs custom A* and DWA (with a Python costmap compatible with Nav2 semantics); Layer D sends commands to the robot SDK or simulation. Orange paths highlight Nav2 ecosystem components often used in industrial ROS 2 deployments.

2 Localization module — detailed flow

Non-technical readers can think of this as “GPS indoors”: instead of satellites, the robot matches laser scans to a pre-recorded 3D map of the building. The EKF (Extended Kalman Filter) smooths jitter so displays and controllers do not “jump.”

Figure 3 — Navigation pipeline (global → local → control)

Figure 3 — Global path is computed once per goal; local DWA reacts every 100 ms to moving obstacles; the controller blends path tracking with DWA when needed.

Why this matters for tenders: The stack combines open, auditable ROS 2 Nav2 components (map server, lifecycle, EKF, tf2) with application-specific Python nodes in navigation_controller, demonstrating both standard industry practice and tailored humanoid behaviour (Manhattan / corridor tuning).

5 Deployment alignment (corridor + machine-facing)

  • Manhattan stack: launch with astar:=manhattan for axis-aligned global paths and single-axis motion (matches crab-style operation).
  • Production localization: use_localization:=true for LiDAR + EKF on site.
  • Goals: define machine access points in the map frame; final orientation faces the equipment.
